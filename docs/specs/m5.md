# M5 Spec — Agent adapter (MCP)

**Status:** Draft. **Milestone:** M5 in `project.md`. **Decisions:** D4, D10. **Builds on:** `docs/specs/m4.md`. **API reference:** `docs/api_spec.md`.

## Goal
An MCP-capable agent, such as Claude, uses an emulated Apple II through an MCP server. The server offers only what a person at the machine could do: type, press keys, move the joystick, look at the screen, listen, and let time pass. With it, the agent completes an example task end to end.

## Non-goals
- Exposing the disk working copies to the agent, and checkpoints in a realtime session. Those are operator concerns (D4); the adapter configures them at launch. (In a stepped session the agent may checkpoint and restore, at the user's request on 2026-10-20: see the checkpoint tools.) (Swapping floppies in drive 1 and 2 *is* exposed: a person at the machine can do that. See "Disk swapping". So is saving a floppy to an image file with `export_disk`, and changing the speed of a realtime session with `set_speed`, both at the user's request after M5.)
- Remote transports. The MCP server uses stdio only.
- Batch orchestration and record/replay. Those are listed as later work.

## Pass conditions
1. **Scripted end to end.** A Python test drives the MCP server through the official MCP client, over stdio, with fixed tool calls:
   1. boot DOS;
   2. type the example program;
   3. `RUN` it;
   4. `read_screen` shows the expected output;
   5. `look` returns a 560×384 PNG image.

   This runs headless in CI.
2. **Text screen.** The harness's `get_text_screen` returns the right lines and mode for:
   - 40-column text (page 1 and page 2);
   - 80-column text;
   - mixed graphics plus text (the bottom 4 lines);
   - full graphics (`mode: "graphics"`, empty lines).

   Inverse and flashing characters decode to plain ASCII.
3. **Agent-only surface.** The MCP server's tool list is exactly the tools below. No operator method is reachable through it, except `insert_disk`, `eject_disk`, `export_disk` and `set_speed` (with `get_speed` when it has no arguments) behind the tools of the same name, and, in a stepped session only, `checkpoint`, `restore_checkpoint`, `list_checkpoints` and `delete_checkpoint`.
4. **Human acceptance.** A person points an MCP-capable agent (Claude Code or Claude Desktop) at the server using the documented config. The agent completes the example task, with the person checking the result. *Human check.*
5. **Disk swapping.** With the server running, the agent ejects the disk in drive 1, inserts another image, and the change is visible: `CATALOG` lists the new disk. Drive 2 can be loaded and emptied the same way. The original image files are never written.

## Harness change: `get_text_screen` (agent method; from M3 ruling R4)
- **Availability:** only when the session was created with `allow_text_screen: true`; otherwise `-32006`.
- **Reply:** `{ mode: "40col" | "80col" | "mixed40" | "mixed80" | "graphics", lines: string[24], emulated_cycles }`.
- **Which page:** decoded from the current video soft switches (TEXT, MIXED, PAGE2, 80COL, 80STORE, ALTCHARSET) and the matching text page in main and auxiliary memory. 80 columns interleave aux and main.
- **Mixed modes:** lines 0–19 are `""` and 20–23 are text.
- **Characters:** each one is mapped to printable ASCII 0x20–0x7E. Inverse, flashing and MouseText characters map to their base character, and MouseText to a space.
- **Formatting:** trailing spaces are kept, so every text line is exactly 40 or 80 characters.

## Adapter: `adapter/applewin_mcp/` (Python 3.12+)
- **Dependency:** the official MCP Python SDK `mcp==2.3.0`, pinned in `adapter/requirements.txt` (MIT licence). It's the only new dependency.
- **Shared client:** the pipe client moves from `tests/python/harness_client.py` to `adapter/applewin_mcp/harness_client.py`. The tests import it from there, so the code isn't duplicated.
- **Launch:** `python -m applewin_mcp --exe <AppleWinHarness.exe> [--headless] [--disk <image>] [--realtime] [--text-screen]`.
  - The adapter starts `--serve` and connects as operator.
  - It calls `create_session { disks, run_mode: stepped (default) or realtime, allow_text_screen }`, then connects as agent.
  - It serves MCP over stdio, and runs `close_session` when it exits.
  - Errors go to stderr. stdout is reserved for MCP.
- **Tools** (names and parameters are fixed; descriptions are written for an LLM):

| Tool | Parameters | What it does |
|---|---|---|
| `type_text` | `text` (string; `\n` = RETURN), `inter_key_delay_ms?` | Types on the keyboard. |
| `press_key` | `key` (char, code or name as `api_spec`), `hold_ms?` | Presses one key. |
| `press_keys` | `keys` (list: a key, `{key, delay_ms?, hold_ms?, wait_for_read?}`, or `{joystick: {x?, y?, buttons?}, delay_ms?, duration_ms?}`), `look?`, `frames?`, `every_ms?`, `region?`, `zoom?`, `delay_from?` (`"applied"` default, or `"read"`; also per entry) | Presses a timed key sequence in one call (post-M5, D10 "Key sequences"; "Read-anchored delays"): with `delay_from` other than `"applied"` the adapter passes it on; the key report gains `(latency L ms)` after a key's read time (read minus applied); sends `press_keys`, waits for its `input_applied`, and returns each entry's applied time and, for a key, its read time in ms from the first entry (a joystick entry has no read time and is reported as `N. joystick  applied T ms`). With `look` true the result is the report followed by the screen as a PNG, taken after the last key's settle frames (no extra stepping); `region`/`zoom` crop it as for `look`. With `frames` (2-16, `every_ms` required; not together with `look`) it skips the settle frames and returns the report plus a line `tile times from the last key's press: ... ms` (each tile's `emulated_cycles` minus the last entry's `applied_cycle`), then a contact sheet as for `look`, its first tile captured as soon as `input_applied` arrives. The strip arguments and sheet size are checked before `press_keys` is sent. A discarded sequence is a tool error (text only). |
| `set_joystick` | `x?`, `y?` (0–255), `button0?`, `button1?`, `duration_ms?` | Moves joystick 0. |
| `wait` | `ms` (1–60,000) | Lets emulated time pass. In stepped mode this is `step_frames` (ms → frames, rounded up). In realtime mode it sleeps the wall-clock time. Typing only takes effect as time passes. |
| `look` | `region?` (`[x, y, w, h]`), `zoom?` (1-8), `frames?` (1-16), `every_ms?` (1-1000) | Returns the screen as an MCP image (PNG, 560×384, borderless): each Apple pixel (280×192) is drawn 2×2. With `region` (Apple pixels, x 0-279, y 0-191; coordinates read off a 560×384 screenshot are halved) and/or `zoom` (default 2) it returns that part of the screen, each Apple pixel drawn zoom×zoom, at most 1120×768. At zoom 2 or more every dot of the 560-dot line is shown (Double Hi-Res, 80-column text); zoom 1 shows every other one. A region or zoom image is built from a `BGRA32` `get_frame` in the adapter. A bad region or zoom is a tool error. With `frames` above 1 (`every_ms` required) it captures that many tiles `every_ms` apart (stepped: `step_frames` of ceil(every_ms×60/1000) between tiles; realtime: sleeps), always through the crop/zoom path so the tiles share one size, and returns the text `tile times: 0.0, 100.1, ... ms` (from each frame's `emulated_cycles`, relative to the first) followed by one PNG contact sheet (4 tiles per row, 2 px grey gaps, at most 1280×1024). Every argument and the sheet size are checked before the first capture, so a rejected call lets no time pass. |
| `wait_until_change` | `timeout_ms` (1-60,000), `region?` (`[x, y, w, h]`), `look?` (default true), `since?` (`"now"` or `"last_input"`, default `"now"`) | Takes a reference frame (`get_frame`) — with `since: "last_input"` instead the frame every input tool (`press_key`, `press_keys`, `type_text`, `set_joystick`) fetches right after its input RPC returns (before the program can have reacted on screen), so a change made during that call is seen at once; a tool error when no input has been sent yet — then lets time pass until any frame pixel inside `region` (Apple pixels, scaled 2x; default the whole screen) differs from it, or `timeout_ms` of emulated time has passed. Stepped: `step_frames` 1 and a `get_frame` per frame. Realtime: `subscribe_frames {every_n_frames: 1}` (unsubscribed again in a `finally`), the latest frame fetched with `get_frame` per iteration (so a change lasting a single frame can be missed), with a wall-clock stop at 2 x `timeout_ms`. `timeout_ms` bounds the emulated time waited in this call; the reported ms is the emulated time since the reference frame (from `emulated_cycles`), rounded, and with `last_input` the text ends ` (since the last input)`. Returns `changed after N ms` or `no change in N ms` (a timeout is not an error), then the whole screen at the end as a PNG (never cropped to `region`) unless `look` is false. Long timeouts take real time to run in a stepped session (it steps and fetches a frame at a time). |
| `read_screen` | — | Returns `get_text_screen` as text: the mode, then 24 lines. Listed only with `--text-screen`. |
| `listen` | `ms?` (0–60,000, default 0) | Runs `wait(ms)` first if `ms > 0`. Returns the sound events (`sound_started`/`sound_stopped`, with duration and `dominant_hz`) received since the last `listen`, as text. The adapter subscribes to audio at launch. |
| `insert_disk` | `drive` (1 or 2), `path` (disk image file), `write_protected?` (default false) | Puts a floppy in slot 6, drive 1 or 2, replacing any disk already there. Like a person swapping disks: the machine keeps running and is not rebooted. A relative `path` is resolved against the adapter's working directory. The adapter rejects paths starting with `\` or `//` (UNC shares and the `\?\` and `\.\` device prefixes) as a tool error, without contacting the harness. |
| `eject_disk` | `drive` (1 or 2) | Takes the floppy out of that drive, leaving it empty. An empty drive is an error. |
| `export_disk` | `drive` (1 or 2), `path` | Saves the floppy in that drive (flushed, so with all writes so far) to a new image file in the same format. Relative paths are taken from the server's working directory; UNC and device paths are rejected by the adapter. The harness never overwrites a file (`-32602`), and an empty drive is an error. |
| `set_speed` | `speed?` (`authentic`, `max` or 0-40), `disk_boost?` (bool) | Realtime sessions only; in stepped mode it is a tool error. Sends `set_speed { machine_speed, enhance_disk_speed }` with only the fields given, or `get_speed` when none are, and reports the resulting speed. |
| `checkpoint` | `name?` (up to 64 characters) | Stepped sessions only: not registered with `--realtime` (user ruling 2026-10-20). Sends the operator `checkpoint` (AppleWin's save state plus the working disks, D5) and returns `saved cp-N (name) at T ms`. The harness limits apply (256 checkpoints, `-32004` beyond). |
| `restore_checkpoint` | `checkpoint_id` | Stepped only. Looks the name up first (`list_checkpoints`; a failure there only drops the name from the message), sends `restore_checkpoint`, then a no-op `subscribe_frames {every_n_frames: 0}` on the agent connection as a barrier (the discarded-input notices and last sound events come on that connection, before its reply), drains them, forgets the sound events not yet reported by `listen` and the `wait_until_change` last-input reference (they belong to the thrown-away timeline), and returns `restored cp-N (name) at T ms`. An unknown id is a tool error. |
| `list_checkpoints` | — | Stepped only. One line per checkpoint, oldest first: `cp-N  name  T ms` (`-` for no name), or `no checkpoints`. |
| `delete_checkpoint` | `checkpoint_id` | Stepped only. Deletes it; an unknown id is a tool error. |

- **Input errors:** a harness error becomes an MCP tool error with the harness message. Tool results are short text, or an image for `look`.

## Disk swapping (harness operator methods, added to M5)
- **`insert_disk`** `{ slot: 6, drive: 1|2, path, write_protected?: bool = false }` → `{}`.
  - `path` must be absolute (`-32602`), and a missing file is `-32005`. Any slot other than 6 is `-32602`.
  - Like `create_session`, it copies the image into the work directory and mounts the copy. The original is never opened for writing (D5).
  - A disk already in the drive is flushed and ejected first. Its working copy is kept until `close_session`.
  - It works in both run modes and takes effect between frames; it doesn't pause or reset the machine.
  - An image AppleWin can't mount is `-32005`, and the drive is left as it was.
  - If the new image fails to mount and putting the previous disk back also fails, the drive is left empty. The reply is `-32005`, with a message ending in `putting the previous disk back failed: <reason>`. The session stays usable.
  - The harness takes any absolute path, UNC included (operators keep full paths). The agent-facing adapter rejects UNC and device paths (see the `insert_disk` tool).
- **`eject_disk`** `{ slot: 6, drive: 1|2 }` → `{}`. It flushes the current track and unmounts the drive. An empty drive is `-32005`.
- **Both:** after a failed restore they return `-32008`. Before a session exists they return `-32002`.
- **Consistency:**
  - `list_disks` reflects every swap.
  - `checkpoint` records the drives as they are, including empty ones.
  - `restore_checkpoint` puts back the checkpointed drive contents, which may differ from the current ones.
  - `export_disk` exports the disk currently in the drive.

## Example task: `adapter/examples/basic_count.md`
- **The task:** "Write and run an Applesoft BASIC program that prints the numbers 1 to 10, one per line." It also gives the success check: after `RUN`, the screen shows 1 to 10.
- **Launch config:** the doc includes the launch config for Claude Code (`.mcp.json` snippet) and Claude Desktop (`claude_desktop_config.json` snippet). The configs use `--disk` with the DOS 3.3 master and `--text-screen`.

## Tests and CI
- **Adapter tests** live in `tests/adapter/` (`unittest`) and use the MCP SDK's stdio client. They cover pass conditions 1 and 3.
- **Disk-swap tests:** C++ or Python pipe tests for `insert_disk` and `eject_disk` (errors, `list_disks`, checkpoint/restore across a swap, originals unchanged), plus an adapter test for pass condition 5.
- **Text-screen tests:** C++ in-process tests write known bytes to the text pages and set the soft switches (`text:` prefix). Python pipe tests cover pass condition 2 end to end.
- **CI:** `pip install -r adapter/requirements.txt`, then run the adapter tests headless after the Python pipe tests.
