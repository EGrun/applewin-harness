# M4 Spec — Checkpoints, state checksum, determinism

**Status:** Draft. **Milestone:** M4 in `project.md`. **Decisions:** D5, D9, D10, D13, D14. **Builds on:** `docs/specs/m3.md`. **API reference:** `docs/api_spec.md`. This spec overrides it where they differ, and the docs task updates it.

## Goal
An operator can checkpoint a session and restore it, and replay from a checkpoint is exact. Restoring the same checkpoint and running the same script always gives the same state checksum, frames and audio, whatever happened before the restore and in either display mode. Working disks can be listed and exported. Original images are never touched.

## Non-goals
- Realtime determinism: realtime runs remain reproducible only in where input lands (D10).
- Audio that doesn't depend on step size. Replays must use the same sequence of run commands (ruling B13). Anchoring each voice by its sample count stays a possible later improvement, recorded in `project.md`.
- Checkpoints that survive the process: they live in the session's work directory and are deleted with it.
- Per-scanline capture, `disk_written` notifications, rate and size limits (M6).

## Pass conditions
1. **Replay** (ruling D4: both scripted runs start from a restore). A stepped DOS 3.3 session takes `checkpoint`, does anything, then `restore_checkpoint` and runs a script mixing `type_text`, `step_frames` and `step_cycles` (it may read the disk, e.g. `CATALOG`: both runs reseed identically, D2). It records `get_state_checksum`, per-step frame hashes and `get_audio` over the script's range.
   - Then unrelated work (keys, a speaker beep, disk-head movement, frames), `restore_checkpoint` again, and the same script.
   - All recorded values must be byte-identical between the two scripted runs. A straight run straight after `checkpoint` is not compared.
2. **Speed.** The same as 1, with the script run once at `machine_speed` 10 and once at 40, in one session. Ruling C7 already makes stepped runs speed-independent; this confirms it end to end.
3. **Display modes.** Pass condition 1's script in a windowed server gives the same checksums, frame hashes and audio as in a headless one (`windowed` suite).
4. **Disks.**
   - A BASIC program is written to the DOS disk (`SAVE`), the disk is exported with `export_disk`, and the export holds the file (its catalog shows it after a fresh boot from the export).
   - The original image's SHA-256 and mtime are unchanged throughout.
   - `restore_checkpoint` to before the `SAVE` brings back the disk without the file.
5. **Speech.** A short BASIC program that drives the Mockingboard's SSI263 speech chip gives the same `get_audio` bytes and frame hashes in both display modes and across two restores of the same checkpoint. If the default Mockingboard config has no SSI263, the implementer configures one (`create_session` gains nothing new: use the slot-4 card AppleWin provides, or report and rule).
6. **Power cycle.** Frames after an in-process `PowerCycle` equal a fresh `Start`'s for the same disk and script. The M1 and M2 goldens still pass.

## Restore purity (the core rule)
`restore_checkpoint` must leave the machine **and the harness** in a state that depends only on the checkpoint. Concretely, after AppleWin's own `Snapshot_LoadState`:
- **Disks.** Before loading, both slot-6 drives are ejected, so AppleWin releases the files. The checkpoint's disk copies are then copied over the working copies. The save state re-inserts them by absolute path, and the files must exist, otherwise AppleWin would open a file dialog.
- **Speed.** The session's speed settings are re-applied (M4-2). `enhance_disk_speed` comes from the session, not the save state.
- **Random numbers.** `srand(1)` is called again (M4-3, D13). The C runtime's stream can't be saved, so it is reset deterministically.
- **Speaker.** Its internals that AppleWin doesn't save are reset with AppleWin's own `SpkrReset()`, plus whatever else the implementer finds is needed (M4-5). The proof is pass condition 1, which restores from two different prior states.
- **Video scanner.** Its phase (`g_dwCyclesThisFrame`) is set from the checkpoint's emulated cycle, consistently with `Start`/`PowerCycle` (pass condition 6). If AppleWin's save state restores it, keep AppleWin's value.
- **Harness state** is cleared (M4-4):
  - **Input queue.** Pending inputs are discarded, and each sends `input_applied { input_id, first_cycle: null, last_cycle: null, discarded: true }` to its connection.
  - **Held keys and buttons** are released.
  - **`AudioCapture`** is cleared, with every voice's position reset. Audio from before the restore is gone, and `get_audio` for it returns `-32009`.
  - **Sound detectors** are reset to the restored cycle.
  - **Frame snapshot.** The presented-frame snapshot is re-rendered from the restored video memory, so `get_frame` straight after a restore shows the restored screen.
- **Cycle origin.** `EmulatedCycles()` continues from the checkpoint's value: the power-on origin is stored in the checkpoint.
- **After the restore** the session is Paused, in both run modes.

`PowerCycle` gets the same video-scanner treatment as Start (M4 parked item, pass condition 6). Audio-capture and detector resets apply there too.

## API (operator, unless noted)
- **`checkpoint { name? }`** returns `{ checkpoint_id, emulated_cycles }`.
  - If Running, it pauses first, at the next present (M4-7: the realtime run ends, so full speed and Mockingboard mute are cleared).
  - It writes `state.yaml` with `Snapshot_SetFilename` and `Snapshot_SaveState`, copies the working disks, and stores the harness metadata: power-on origin, emulated cycle, speed settings and name.
  - Location: `<work>/checkpoints/<checkpoint_id>/`. `checkpoint_id` is `cp-<n>` with *n* counting up from 1.
  - Errors: a failure is `-32004` with the cause. More than 256 checkpoints is `-32004`.
  - `name` is optional, up to 64 printable characters; otherwise `-32602`.
- **`restore_checkpoint { checkpoint_id }`** returns `{ emulated_cycles }`, as described above. An unknown id is `-32602`; a load failure is `-32004`, and the session is then unusable (it replies `-32008` to run commands until `close_session`).
- **`list_checkpoints {}`** returns `[ { checkpoint_id, name, created_at (ISO 8601 UTC), emulated_cycles } ]`, oldest first.
- **`delete_checkpoint { checkpoint_id }`** returns `{}`.
- **`get_state_checksum {}`** returns `{ sha256, emulated_cycles }`.
  - The SHA-256 is over a fixed, documented byte layout:
    1. CPU registers A, X, Y, P, S, PC;
    2. the memory mode (`GetMemMode()`);
    3. all main and auxiliary RAM, including the language-card banks, taken as `MemSaveSnapshot` takes it (flushing the shadow/dirty pages first);
    4. the keyboard latch and strobe;
    5. the video soft-switch mode;
    6. the Disk II controller state (motor, current drive, each drive's phase and track).
  - Never wall-clock, paths or harness bookkeeping. The exact layout is written into `api_spec.md`.
  - **Agent use:** `get_state_checksum` is an operator method.
- **`step_cycles { cycles: 1..17030000 }`** runs exactly that many cycles in stepped mode. Like `step_frames`, it may overshoot by the last instruction and pauses first if Running. It replies `{ emulated_cycles }`.
- **`list_disks {}`** returns `[ { slot: 6, drive: 1|2, original_path, working_path, write_protected, format } ]`, with empty drives left out. `format` is the image type AppleWin reports (e.g. `"DO"`).
- **`export_disk { slot: 6, drive, dest_path }`**:
  - Flushes the current track (`FlushCurrentTrack`), then copies the working image to `dest_path`, and returns `{}`.
  - `dest_path` must be absolute, must not exist, must not be any session's original image, and must not be inside the harness work directory. Otherwise `-32602`.
  - An empty drive is `-32005`.

## Errors
As in `api_spec.md`, with `-32004` for checkpoint failures.
